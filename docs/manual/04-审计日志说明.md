## 1. 谁能看什么

| 角色 | 范围 |
| --- | --- |
| 普通用户（member） | 只能查**本人作为操作人**产生的日志 |
| 管理员（admin） | 查**全量**日志、做完整性校验、导出 CSV |

入口：

- **admin**：管理中心 → 审计日志（`/admin/audit-logs`），多维筛选。
- **普通用户**：可查本人操作记录（后端 `GET /api/v1/audit-logs` 自动按本人过滤）。

## 2. 审计日志里记录了哪些字段

每一条日志（`audit_logs`）包含：

| 字段 | 说明 |
| --- | --- |
| `seq` | 链序号，单调递增、无缺口 |
| `occurred_at` | 事件时间（UTC 存，前端按本地时区显示） |
| `actor_type` | `user`（用户）或 `api_key`（API Key 调用） |
| `actor_name` | 调用人：用户名，或 Key 的名称/前缀 |
| `action` | 操作类型枚举（见下） |
| `object_type` / `object_id` | 对象类型（template/document/job/signature/seal/settings/auth…）与对象 id |
| `template_code` | 冗余的模板编号，便于筛选 |
| `external_ref` | 投递业务单号（幂等键） |
| `signature_id` | 本次用了哪个签名（`sig_xxx`，可空） |
| `seal_id` | 本次用了哪个印章（`seal_xxx`，可空） |
| `source_ip` | 来源 IP |
| `endpoint` | 接口 `方法+路径`（如 `POST /api/v1/generate`） |
| `detail` | 补充 JSON：前后差异、错误码、剩余次数等 |
| `prev_hash` / `self_hash` | 哈希链字段（见 §4） |

在审计日志页，行展开可以看到 `detail` 与 `endpoint` 的完整内容。

## 3. 可审计的操作类型

| 动作 action | 触发点 |
| --- | --- |
| `template.upload / edit / version / rollback / disable` | 模板上传、编辑、版本、回滚、停用 |
| `document.generate / export / retry` | 生成、导出、重试（含 template_code、external_ref、用了哪个签名/印章） |
| `signature.create / update / delete / use` | 签名的增删改、每次实际使用 |
| `seal.create / update / delete / use` | 印章的增删改、每次实际使用 |
| `signature.use.denied` / `seal.use.denied` | 签章被拒（未授权/耗尽/过期） |
| `signature.grant.create / renew / revoke` | 签名授权的授予/续期/吊销 |
| `seal.grant.create / renew / revoke` | 印章授权的授予/续期/吊销 |
| `review.approve / review.reject` | 审核通过/驳回（含审核人、意见） |
| `auth.login / auth.logout` | 登录成功/失败、登出（含 IP） |
| `key.create / disable` | API Key 创建、停用 |
| `settings.update` | 系统设置改动 |

> 授权流水（授予/使用/续期/吊销/拒绝）并入同一条哈希链，不另起链。

## 4. 完整性校验：哈希链

### 4.1 原理

每条日志的内容（除哈希字段外）按固定顺序序列化为 canonical JSON，然后：

```
self_hash = SHA256( prev_hash + "|" + canonical_payload )
```

- 第一条（创世）：`prev_hash` = 64 个 `0`。
- 每条的 `prev_hash` = 上一条的 `self_hash`。
- 写入在**单个数据库事务**内串行完成（行锁取尾条），保证 `seq` 单调无缺口、哈希环环相扣。

任何一条日志的内容被改动，它的 `self_hash` 就变了，后面所有条目的 `prev_hash` 都会对不上——链条立刻断。

### 4.2 校验接口

```
GET /api/v1/admin/audit-logs/verify
```

从头重算全链，返回：

```json
{ "ok": true, "checked": 512 }
```

断链时：

```json
{
  "ok": false,
  "checked": 512,
  "broken_at_seq": 128,
  "expected_hash": "...",
  "actual_hash": "..."
}
```

- `ok=true`：链路完整。
- `ok=false`：`broken_at_seq` 精确定位到**第一条对不上的记录序号**，并给出期望哈希与实际哈希。

在审计日志页点「完整性校验」按钮即可触发，页头状态条会显示"链路完整（最近校验时间、共 N 条）"；断链时顶部红色 Alert 提示"第 128 条哈希不一致，疑似被篡改"。

## 5. 导出 CSV

```
GET /api/v1/admin/audit-logs/export?object_type=&object_id=&from=&to=
```

导出为 `audit.csv`。文件**前 5 行是 # 开头的校验头（sidecar）**：

```
# zhuban audit export
# range_start_prev_hash=<导出区间首条的 prev_hash>
# range_end_self_hash=<导出区间末条的 self_hash>
# count=<导出条数>
# exported_at=<UTC 时间>
seq,actor_type,actor_user_id,actor_name,action,object_type,object_id,occurred_at,prev_hash,self_hash
...
```

外部方可凭"首条 prev_hash + 末条 self_hash + 条数"对照全链规则复核这份导出有没有被截取或改动。

## 6. 为什么它不可篡改

1. **应用层没有任何 update / delete 接口。** 角色再高也改不了——`audit_logs` 只开放 INSERT 与 SELECT，不提供修改/删除 handler。
2. **哈希链环环相扣。** 在库里改一条，从那一条开始全链断裂，校验接口精确定位 `broken_at_seq`。
3. **写在事务里。** 并发写入不会产生 seq 缺口或哈希错位。
4. **建议运维层再加一道**（WORM）：数据库账户对 `audit_logs` 只授 INSERT/SELECT，回收 UPDATE/DELETE；定期 `pg_dump` 冷存，日志表不参与过期清理。

> 诚实边界：哈希链只能防"库内被改"，不等于法律存证/区块链存证。它让任何篡改都会被立刻发现，而不是让篡改不可能发生。
