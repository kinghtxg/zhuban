# 演示模板与表格行循环修复（2026-10-29）

> 起因：开源版要一个「每个功能都演示到位」的新演示模板。做模板的过程中，把
> 模板本身当成验收用例跑了一遍真实渲染，撞出两个一直存在的静默缺陷。
>
> 结论先说：**表格行循环（`{%tr for %}`）在产品里从来没跑通过**，而手册 §4
> 教的就是这个写法；扫描器另有四处会把变量清单扫错，错了也不报错。

---

## 1. 表格行循环：`{%tr for %}` 与 `{%tr endfor %}` 写在同一行时必然失败

### 症状

手册 §4「表格行循环」的写法——`{%tr for it in items %}` 写在首格开头、
`{%tr endfor %}` 写在末格末尾——渲染直接失败：

```
SecurityError: 渲染失败：Encountered unknown tag 'endfor'.
```

报错里完全看不出跟表格有关，很容易被误判成「模板标签配对写错了」而去改模板。
用**原生 docxtpl 0.20.2**、最小两行表格复现，同样失败 —— 不是我们这条链路的
问题，是上游实现的问题。

### 根因

docxtpl 的 `patch_xml` 用这条正则处理行级标签：

```
<w:tr[ >](?:(?!<w:tr[ >]).)*({%|{{)tr ([^}%]*(?:%}|}})).*?</w:tr>
```

前缀 `(?:(?!<w:tr[ >]).)*` 是**贪婪**的，会一路吃到这一行结束，再回溯去找
`{%tr `。回溯是自右向左的，于是取到的是这一行里**最后一个** `{%tr` 标签 ——
也就是末格的 `{%tr endfor %}`。整行被替换成 `{% endfor %}`，首格的
`{%tr for %}` 连同整行内容一起消失，Jinja 编译时就报「多出来的 endfor」。

换句话说：这个语法只有在「一行里恰好只有一个 `{%tr` 标签」时才是对的，
而常见写法恰恰是两个。

### 做法

在预处理层（`render-service/app/preprocess.py: _normalize_row_tags`）自己把
行级标签搬到行外，搬完之后 XML 里再无 `{%tr %}`，docxtpl 那条正则没有机会
误伤：

| 模板里写的 | 搬到哪 |
|---|---|
| `{%tr for X in Y %}`（在该行某格） | 该 `<w:tr>` **之前** → `{% for X in Y %}`，整行成为循环体 |
| `{%tr endfor %}` | 该 `<w:tr>` **之后** → `{% endfor %}` |
| `{%tr if %}` / `{%tr else %}` | 同上，`if` 类在行前 |
| `{%tr endif %}` | 行后 |

两种写法都支持：

- **同格写法**（手册约定）：首格 for、末格 endfor，行内有内容 → 保留该行，前后夹标签；
- **独占行写法**：`{%tr for %}` 单独占一行 → 把标签挪到前一个兄弟节点后，**整行删掉**，
  否则成品里会多出一条空行。

`{%tr vm %}` / `{%tr hm %}` / `{%tr colspan %}` 是单元格级指令，原样留给 docxtpl。

## 2. 扫描器：四处「扫错了也不报错」

| # | 症状 | 根因 | 后果 |
|---|---|---|---|
| 2.1 | `{% if 风险等级 == "高" %}` 的枚举提取不到 | `cmp_re` 的左侧用 `IDENT`（只认 ASCII）匹配，中文字段名永远不中 | 枚举校验形同虚设，写成「高危」条件块静默消失 |
| 2.2 | 枚举提取到了也不拦 | `render.py: validate_data` 里没有任何按 enum 校验的分支 | 同上，且接口 200 |
| 2.3 | 两个循环都用 `it` 时字段互相串 | `_build_variables` 的栈只存变量名，按名字归属字段 | 交付清单被塞进内层循环的「问题/等级/建议」，自己的「完成/备注」反丢失 |
| 2.4 | `{{ it.备注 or "—" }}`、`{{ it.完成 if ok else "" }}`、`{{ g.条目 \| length }}` 里的字段扫不出来 | 点引用正则整串锚定 `$` | 用户看不到也填不了，成品那两列永远是空的 |

另外两处顺带修掉：

- **条件里的字符串字面量被当成变量**（`"高"` → 变量「高」），已在上一轮修；
- **嵌套循环被平铺成顶层变量**（`g.条目`）：示例 JSON 里它排在最外层，用户照着填，
  父项里没有 `条目`，Jinja 对缺失属性抛 `UndefinedError` 整单失败；即便不抛，
  生成的表格也是空表。现在识别为父循环的一个数组字段（`kind=loop`、`nested=true`），
  示例数据嵌套在父项内部。

枚举字段的**示例值取枚举里的第一个值**，不再填「（待填）」——否则用户下载的
示例 JSON 本身就通不过自己的枚举校验，第一次投递就被拦下。

### 证据

```text
tests/test_scan_semantics.py  10 passed
  test_enum_from_chinese_comparison / test_enum_single_quote_and_multi_value
  test_enum_does_not_create_ghost_condition / test_dotted_ref_with_suffix
  test_string_literal_not_a_field / test_same_loop_var_does_not_cross_contaminate
  test_nested_loop_attached_to_parent / test_validate_rejects_bad_enum
  test_validate_rejects_bad_enum_inside_loop / test_validate_rejects_bad_enum_inside_nested_loop
```

演示模板实测：`风险等级.enum == ["高"]`，`交付清单` 字段为
`名称/完成/备注`，`问题分组` 字段为 `分组` + 数组字段 `条目`，
`POST /validate` 传 `风险等级=高危` → `取值必须是 高 之一（当前为「高危」）`。

## 3. 演示模板本身

`samples/tools/build-demo-template.py` 生成 `samples/templates/demo-report.docx`
（脚本可复现、可 diff、带自检），覆盖：

标量 · 默认值 `|default` · 日期表达式 `$date` · 表格行循环 `{%tr for %}` ·
整段循环 `{%p for %}` · **嵌套循环**（分组 → 组内条目） · 条件与 `{% else %}` ·
行内条件表达式（`{{ "已完成" if it.完成 else "进行中" }}`） · 图片 · 二维码 ·
富文本（markdown） · 折线图 + 饼图（数据可变、样式不动） · 签章占位 ·
页眉页脚页码 · 目录域（TOC）。

每次改模板后必须跑真实渲染（不能只看扫描结果）：

```bash
cd render-service && python - <<'PY'
import json, zipfile, io
from lxml import etree
from app.render import render_template
raw = open('../samples/templates/demo-report.docx','rb').read()
data = json.load(open('../samples/demo-report.sample.json', encoding='utf-8'))
out = render_template(raw, data)
txt = ''.join(etree.fromstring(zipfile.ZipFile(io.BytesIO(out)).read('word/document.xml')).itertext())
assert '{{' not in txt and '{%' not in txt   # 无残留标签
print('ok', len(out))
PY
```

**教训**：扫描器只保证「标签能被解析」，不保证「能渲染出来」。扫描全绿 + 0 诊断
的模板，照样可能在真实渲染时整份失败 —— 演示模板就是这么把行循环的问题炸出来的。
新增/修改模板的验收标准必须包含一次真实渲染。

## 4. 内置模板播种

（内部公司名 → `示例科技有限公司`，内部项目号 → `DEMO-2026-001`）：
这份文件会被播种进用户数据库并作为「一键试用」数据展示，属于对外内容。
